# CLI cheatsheet

Every command is a thin call to the local daemon, which lazy-starts on first use. The skill always passes `--session "$CLAUDE_CODE_SESSION_ID"` and `--cwd "$PWD"`; the daemon resolves the review from the session id and repo root, so you never pass a review id.

| Command | What it does |
| --- | --- |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" start --session <id> --cwd <dir> [--new] [--base <ref>] [--pr <ref>] [--open]` | Snapshot the working tree and print the review URL, zero or more `tailnet: <url>` lines when synckit's mesh trust is on, each the same review on one of the daemon's tailnet addresses, a `channel: active\|pending\|inactive` line (`active`: this window's channel is proven and attached — skip the Monitor; `pending`: channel server wired but unproven — arm the Monitor; `inactive`: no channel consumer — arm the Monitor), a `setup: {"offer":…,"reason":…}` line (the first-run channel-approval offer), and an `organize: <AI request JSON>` line carrying the daemon's eager organize request — printed when a new version was created, and re-offered with the same id when an unchanged resume finds the latest version still unorganized. By default it resumes this window's open review (following `/clear`/resume rotation; an orphaned review from an exited window is adopted), and `--new` forces a fresh one. A new review pins its diff base to HEAD when the working tree is dirty, to the trunk fork point when clean so the whole branch is reviewed, or to `--base <ref>`. Later snapshots diff against the pin; with nothing to review, start exits non-zero saying `no changes to review`. In a Graphite-tracked repo it starts a **stack review** instead (auto-detected): one section per stacked branch diffed against its parent, plus a pending section for the uncommitted working tree, and a `stack: {"trunk":…,"branches":[…]}` line after `setup:`. A stack review pins nothing — every snapshot re-resolves the stack — and `--base <ref>` forces a flat single-diff review. `--pr <url\|owner/name#N\|#N\|N>` starts a **PR review** instead: the PR's whole stack from GitHub, one section per PR, comments synced both ways, plus a `pr: owner/name#N (stack: #a #b #c)` line in place of `stack:`, and a `github` key in the `setup:` JSON when Claude's GitHub replies can't post yet: `cc-review github setup`, the App's install URL, or the check's error. `--pr` and `--base` are mutually exclusive. `--open` opens the review URL in the browser after printing it, in either mode. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" watch --session <id> --cwd <dir> [--once]` | Print one JSON event per line (events you originate — your replies and MCP tool calls — are filtered out) and exit on `submit`. `--once` exits after the **first** event instead, resuming from its cursor next launch — for a per-event relay loop. Run continuous under a persistent Monitor (`route-monitor`), or `--once` from a streamer teammate (`route-teams`), a streamer subagent (`route-streamer`), or inline (`route-inline`). |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" reply --comment <id> --kind <question\|ask\|clarification> --body <text> [--header <chip>] [--multi-select] [--options-json <json>]` | Post a reply under a comment. Returns immediately. `--kind ask` requires `--body` and `--options-json`, a JSON array of `{label, description?, preview?}`; `--header` is a short chip like "Approach"; `--multi-select` allows multiple picks. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" reply --answer-to <replyId> --select <label> [--select <label>] [--other <text>] [--notes <note>]` \| `--answer <text>` | Record the human's answer during the post-submit drain: `--select`/`--other`/`--notes` for an `ask` target, `--answer` only for a plain `question` target. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" feedback --session <id> --cwd <dir>` | Print the frozen feedback JSON (`threads` + `open_questions`) after Submit. Every thread and open question carries `branch` and `pending`: `pending: true` means the comment sits on working-tree hunks (and `branch` is empty); otherwise `branch` names the stack branch that owns it. Threads carry `version_number` — below the feedback's `version` means the thread was stranded by a mid-round version bump; apply it with re-checked line anchors. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" github setup [--org <org>]` \| `github status [--cwd <dir>]` | The human's commands for PR mode. `setup` prints `open: <url>` and a `tailnet: <url>` line per tailnet address the daemon serves, opens the daemon's setup page, waits up to 10 minutes for the user to create the App on GitHub (under `--org` when given), then prints `app: <slug>` and `install: <url>`. `status` prints `app:`, `bot:`, and `install:` lines for the cwd's repo, or ``app: not set up; run `cc-review github setup` `` when there's no App. `setup` needs the user in a browser to confirm on GitHub, so when `start --pr` prints a `setup:` line, hand it to the user. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" status [--session <id> --cwd <dir>]` | Show daemon and review status. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" stop` | Stop the background daemon. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" setup-channels [--check\|--apply\|--decline]` | Approve cc-review's channel. The skill reads the offer from `start`'s `setup:` line, not from `--check` (which prints the same `{offer,reason}` and remains for manual use); `--apply` writes the approved-channels config (admin prompt); `--decline` records a no. See `channels-setup.md`. |
| `"${CLAUDE_PLUGIN_ROOT}/bin/cc-review" channel-ack --session <id> --cwd <dir>` | Mark this window's channel proven after the first delivered `<channel>` tag, flipping later `start`s to `channel: active`. Hidden, like `setup-channels`. Run it once when a tag arrives while the Monitor is armed, then stop the Monitor. |

The daemon keeps derived state under `~/.cc-review/v1` (sqlite db, per-review patch + feedback files, the control socket, and the HTTP handshake). It is never relocated by an environment variable.
